# Load test: 100 people on casa (M7, D21)

Run 2026-10-12 against production (zoom3d.pyldin601.xyz, `sha-791c5e8`, 6d fan-out live), from a MacBook on the
same LAN (Wi-Fi), through the router like any visitor. casa: one k3s node, 4 cores, shared with other services
(14% CPU at idle).

## Verdict

**A 100-person room fits on casa.** Everything held with no loss, no move corrections and a 60 fps browser in the
crowd. The modelled full load (see "Scaling to the full model") lands at an estimated **75–85% node CPU**, and
**~265 Mbit/s** of LiveKit egress. That is enough but not roomy. The untested limits are casa's **internet uplink**
(real people are remote; every byte here stayed on the LAN) and LiveKit's **ingest from 100 real publishers**.

## Method

| Part | Tool | What it models |
|---|---|---|
| Game socket | `apps/server/load-test/swarm.ts` | N real WebSocket clients in one room, walking LEVEL1 at player speed (3 tiles/s) and sending `state` at 15 Hz like the browser, each with a picture |
| Media | `lk load-test` (livekit-cli 2.19) | 12 video publishers (`--video-resolution low`, simulcast) + 24 audio publishers, received by N subscribers: what one zoom3d client receives at the 6c caps (12 faces, 24 voices) |
| Browser | `apps/web/load-test/fps.ts` | Real Chrome (fake camera) joining the swarm's room, measuring frame rate with `requestAnimationFrame`; 2 more fake-camera browsers join first so it also decodes faces |
| Metrics | `scripts/load-test-snap.py` | Prometheus (port-forwarded to :9090): node CPU and NIC, per-container CPU, server event loop, LiveKit bytes |

Commands:

```bash
kubectl -n monitoring port-forward svc/prometheus-server 9090:80 &
(cd apps/server && pnpm exec tsx load-test/swarm.ts wss://zoom3d.pyldin601.xyz/ws <roomId> 100 240)
(cd apps/web && node load-test/fps.ts https://zoom3d.pyldin601.xyz/r/<roomId> 2 150)
LIVEKIT_API_KEY=… LIVEKIT_API_SECRET=… lk load-test --url wss://lk.pyldin601.xyz --room lt \
  --video-publishers 12 --audio-publishers 24 --subscribers 100 --video-resolution low --layout 4x4 \
  --num-per-second 10 --duration 150s
python3 scripts/load-test-snap.py 2m
```

The keys are in the `livekit-keys` secret (namespace `zoom3d`).

## Results

### Game socket (6d fan-out)

| Clients | Server CPU | Event loop p99 | Server RSS | Batches out | Per client | Node CPU |
|---|---|---|---|---|---|---|
| 0 (idle) | 0.01 cores | 10 ms | 91 MiB | 0 | – | 14% |
| 50 | 0.15–0.18 cores | 21–24 ms | 100 MiB | 560–650/s, 3.4–3.8 Mbit/s | 30 msg/s, 40–150 kbit/s | 25–29% |
| 100 + 3 browsers | 0.35 cores | 36 ms | 105 MiB | 1,535/s, 17.8 Mbit/s | 30 msg/s, 170–280 kbit/s, 60–96 poses per batch | 27% |

- **Zero move corrections** throughout: every state from 100 walkers passed the plausibility check.
- **Browser in the crowd:** 60.0 fps, p95 frame 16.8 ms, worst 17 ms, with 102 others in view range and two live
  faces.
- **Per-client bytes grow with how many people are near** (16 tiles). Clustered at spawn, everyone is near: ~95
  poses per batch, 280 kbit/s. Spread out, ~60 poses and 170 kbit/s. Before 6d the same 100 cost ~1,000 messages/s
  per client.

### Media (LiveKit)

| Subscribers | LiveKit CPU | LiveKit out | Per subscriber | Loss | Node CPU |
|---|---|---|---|---|---|
| 25 | 0.8 cores | 21 Mbit/s | 1.5 Mbit/s | 0% | 34% |
| 100 | 1.3–1.8 cores | 180 Mbit/s | 1.6 Mbit/s | 0%, no NACKs | 52% |

`lk` subscribed each tester to about two-thirds of the 36 tracks (2,437 of 3,600 at 100 subscribers: 837 video,
1,600 audio). This looks like a counting quirk in `lk load-test`, so the numbers are per forwarded track and
scaled below.

### Both at once (100 game clients + 100 media subscribers)

Node CPU **~60%**. LiveKit 1.4–1.7 cores, game server 0.2 cores (event loop p99 25 ms), LiveKit out 172 Mbit/s
(243 Mbit/s on the NIC). 0% media loss; game clients at 30 msg/s with no corrections.

## Scaling to the full model

Real 100 people at the 6c caps forward about 3,600 tracks, 1.48× what was tested:

- **LiveKit:** ~2.2–2.6 cores and ~265 Mbit/s out. Node CPU ≈ 14% baseline + ~55–65 points (LiveKit) + ~5 points
  (game server) ≈ **75–85%**.
- **Ingest, not tested:** 100 real publishers each upload a mic and the face sizes someone wants (dynacast), about
  50 Mbit/s into LiveKit against 36 publishers here.
- **Memory:** LiveKit peaked at ~1.07 GiB working set with 136 participants (idle: 52 MiB). The limit is 2 GiB, so
  watch it at full load. After the rooms closed the Go heap dropped back to 74 MiB within 4 minutes: no leak.

## Caveats

- **Uplink:** all traffic stayed on the LAN (the router hairpins). Remote people would need ~265 Mbit/s up from
  casa's internet line, which this test did not touch. Check the line's real upstream before inviting 100.
- **Wi-Fi:** the generator was on Wi-Fi. A few windows showed bunched batch arrivals (two within 15 ms) while the
  generator's own loop was fine (≤ 30 ms lag). They're likely Wi-Fi bursts; the server-side numbers were steady
  meanwhile.
- **`lk` subscribers don't decode;** browser decode cost was measured with 2 real faces only.
- The first attempt overlapped another session's parallel e2e runs (Mac load ~30). That stalled the generator, so
  those runs were discarded and repeated on a quiet machine.

## Follow-ups

- Measure casa's real upstream bandwidth (speed test from the node) before a 100-person event.
- Optional: hysteresis on the fan-out tier boundary (see the 6d spec's known gap).
- `MAX_PEERS = 128` stands; raising it needs the uplink number first.
