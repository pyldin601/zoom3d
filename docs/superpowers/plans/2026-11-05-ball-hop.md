# Ball Hop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The ball visibly hops once when kicked and repeatedly while playing, with no change to its physics.

**Architecture:** A small pure simulation (`game/ball-hop.ts`) owned by `BallPrediction` gives a height. `remote-world.ts` copies it into a new `VoxelInstance.lift`, which the projection, lighting and lamp shadows all honour.

**Tech Stack:** TypeScript, vitest, the software renderer in `apps/web/src/renderer`.

**Spec:** `docs/superpowers/specs/2026-11-05-ball-hop-design.md`

## Global Constraints

- No server, protocol, snapshot or `stepBall` change.
- A lift of 0 draws pixel for pixel as today: `pnpm bench:sprites` and `pnpm bench:walls` hashes stay the same.
- No allocations per frame.
- A scared ball keeps its tremble and doesn't hop. Only `playing` hops by mood.
- Starting values: kick 0.35 tiles, playing 0.15 tiles, 0.3 s between play hops, gravity 3 tiles/s².
- Code style: `docs/code-style.md`, braced blocks, names with units, no "you/your" in identifiers, comments or test titles.

## Review Focus

- Kicking again and again in mid-air: the ball never rises past the 0.35-tile apex, so its top stays under the 0.85 lamps (a higher one would make `shadowReach` divide by zero or less). Pinned in Task 1.
- A long `dt` after a hidden tab: it lands at exactly 0 and doesn't sink below the floor or start from a stale speed. Pinned in Task 1.
- The local player's kick echo: it must not launch a second hop. Pinned in Task 4.
- A new welcome (`reset`) while in mid-air: the ball starts on the floor. Pinned in Task 4.
- The vacuum's knock arrives as a `kick` event with no `by`, so it hops the ball too. That follows "a kicked ball hops"; pinned in Task 4, and worth the owner's eye.

- [ ] **Step 3: Implement `apps/web/src/game/ball-hop.ts`**

`stepBallHop` integrates `liftTiles` and `upSpeed` under gravity. Landing sets both to 0. A launch aims at an apex, never adds speed: `upSpeed = Math.sqrt(2 * GRAVITY * (apex - liftTiles))`, only when `liftTiles < apex`. That is what caps repeated kicks. On the floor and `mood === 'playing'`, `restS` counts down; at 0 it launches to `PLAY_HOP_TILES` and resets `restS` to `PLAY_HOP_GAP_S`. In any other mood `restS` is 0, so play starts with a hop at once.

- [ ] **Step 3: Implement**

`BallPrediction` holds one `BallHop`. `kick` calls `kickBallHop` on success. `server` calls it when `m.event === 'kick' && (m.by === undefined || m.by !== selfId)`, the rule `object-sounds.ts` uses. `step` calls `stepBallHop(hop, dt, shownMood)` after `shownMood` is set and after the no-ball return. `reset` replaces the hop state's values, and `lift` reads `hop.liftTiles`. `remote-world.ts` stores `ballLift` from `sample` and sets `v.lift` in `collectVoxels` by kind. `room-loop.ts` passes `room.ball.lift` at both calls.
